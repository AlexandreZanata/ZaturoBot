# 04 — Integration contracts

Status: proposed contracts, not live endpoints, migrations, Rust types or permissions. Depends on [architecture](03-SYSTEM-ARCHITECTURE.md), [autonomy](06-AUTONOMY-AND-POLICY-MATRIX.md), [platform gates](07-PLATFORM-COMPLIANCE.md) and the [audited baseline](01-REPOSITORY-AUDIT.md).

## Contract ownership and transport

Keep independent databases. Zaturo owns campaigns, verified offer facts, BrandKit revisions, grants, TaskId/OperationId and aggregated commercial results. MeuAssistente owns conversation identity, ownership/handoff, recipient consent, incoming claims and communication receipts. Each endpoint calls its own Services; SQL and transactions never cross repositories. A communication receipt is evidence attached to one Hub operation, not another campaign task lifecycle.

Propose private HTTP JSON under `/commerce/v1`, with authenticated TLS, VPN or the already approved authenticated SSH transport. Bind loopback by default; private reachability alone is insufficient authentication. Provision dedicated opaque service credentials independently for each direction and target audience. Targets store only constant-time-verifiable token digests and an owner-provisioned principal record: enabled status, expiry, credential revision, allowed agency/campaign/account/channel, exact capabilities and rate limits. No owner/worker token reuse, browser dashboard login reuse, cookie extraction, credential in URLs or credential forwarding to models. Cross-network transport and credential provisioning require implementation review and explicit setup authority.

Initial capabilities are `commerce.facts.read.v1`, `commerce.report.append.v1`, `communication.status.read.v1` and `communication.draft.request.v1`. Future separately granted `communication.send.v1` does not include consent editing, human release, group enrollment, campaign editing or financial operations. MeuAssistente may read verified facts without any send capability. Public health exposes no campaign, recipient or authorization metadata.

Version identity consists of path major version and strict `schema_version: 1`. Unknown required versions, variants or fields fail closed. No automatic downgrade. Wire types belong in protocol; source schemas generate documentation and fixtures. The Hub/worker protocol remains version 2 / 16 KiB at baseline: a proposed 32 KiB service envelope does not fit it. Worker assignments carry bounded IDs and hashes; large facts/manifests use separately authenticated bounded artifact retrieval, or a deliberately negotiated protocol change with old-peer denial tests.

## Common envelope and identity

A request has `request_id`, `operation_id`, `task_id`, `agency_id`, `campaign_id`, `campaign_revision`, `grant_id`, `grant_revision`, `schema_version`, `created_at_utc`, `expires_at_utc` and typed `payload`. The caller supplies references; authentication supplies its principal and allowed scope. The server validates both and must not deserialize an actor/role/capability from payload as authority. Read requests omit irrelevant task/grant fields and require the corresponding read capability. Timestamps use UTC with millisecond precision; local editorial interpretation retains an IANA timezone separately.

Mutations require `Idempotency-Key` (1..128 canonical ASCII bytes) and a SHA-256 fingerprint of the canonical validated semantic payload, including endpoint version, principal scope, account, immutable content hash and expected revisions. Transport request ID/timeouts are not new business operation identities. A new HTTP request or refreshed credential can query/replay the same operation; changing identity to bypass an unresolved receipt is forbidden. Reject inconsistent OperationId/task/campaign bindings.

Successful responses contain `request_id`, `operation_id`, server time, resource revision and typed `data`. Errors contain stable `code`, safe `message`, optional `current_revision`, `retry_after_seconds` and `retry_class` (`never`, `read_only`, `proven_no_effect`, `reconcile`). Do not return prompts, provider bodies, recipient labels, phone numbers, access tokens or raw messages in errors. A retry class is advice constrained by the durable operation ledger, never permission to repeat a possible side effect.

## Immutable facts and content schemas

`EvidenceRef` records evidence ID, source kind (`owner_verified`, `official_api`, `authorized_report`), canonical source reference, observation time, source account/program scope, rights/terms evidence reference, hash of retained material, and expiry/revalidation rule. A public URL proves neither scraping permission nor truth. Do not ask a model to generate evidence. Evidence bodies remain bounded worker artifacts when needed; the Hub receives references/minimized facts, not account pages or customer data.

`ProductSnapshot` contains immutable product ID/revision, source platform/product/variant IDs, approved title/specification fields, source evidence IDs, observed time, valid-until time, availability (`in_stock`, `out_of_stock`, `unknown`) and claim limitations. Variant, region, freight, coupons and payment conditions are explicit; missing values are unknown. A product specification cannot support an assertion of physical testing or guaranteed performance.

`OfferSnapshot` adds offer ID/revision, product snapshot/hash, currency ISO code, integer price in that currency's minor units, currency exponent, optional separately evidenced reference price, eligibility/coupon/shipping conditions, observation/valid-until times, source evidence IDs and official affiliate-link reference. No floating-point money or cross-currency totals; validate currency/exponent against a reviewed supported set. The initial BRL pilot uses exponent 2. A discount percentage is a deterministic calculation from comparable current/reference evidence, otherwise absent. Never derive history from a single current price.

`AffiliateLink` stores the exact owner/program-provided official URL, platform/program/account identity, product binding, allowed channel/link form, creation/expiry evidence and disclosure requirements. Validate HTTPS, approved exact hosts and account/product binding without opening arbitrary redirects. Keep its original encoded bytes for publication; do not shorten, decorate, replace parameters or add tracking unless the program expressly permits that exact transformation. A changed link creates a new revision and revalidation. A blocked or unverifiable link cannot be published.

`BrandKitManifest` contains kit ID/revision/hash, approved display name, voice/positioning rules, locale, palette/contrast results, licensed font references, logo/avatar/banner/template artifact hashes, dimensions/safe areas, alt-text rules, disclosure placement and owner acceptance reference. Every asset has provenance/license evidence and content hash. The manifest is immutable; no inline media or arbitrary local paths. Changing a pinned brand revision invalidates affected drafts/approvals and requires a new content manifest.

`ContentManifest` contains content ID/revision/hash, campaign revision, BrandKit hash, target account/channel/format, exact rendered text/hash, media artifact hashes, alt text, source offer/evidence revisions, required advertising/affiliate disclosure, review state and intended publication window. Facts are rendered by deterministic validation; model output is a candidate. All material claims must point to supporting evidence or be removed. The publisher receives an immutable manifest, not free-form instructions to improvise facts.

Proposed freshness rule for the small pilot: source-defined expiry always wins; price/availability-bearing content requires verification within 15 minutes before dispatch and before the offer expires. This is a conservative proposed maximum, not a claim of platform correctness; stricter source terms override it. If authorized refresh is unavailable, omit price-dependent claims only through a new reviewed manifest or block publication. Never silently edit queued text. Signed/authorized source data can impose a shorter TTL; arbitrary caller TTL cannot lengthen it.

## Proposed endpoints and result semantics

On Zaturo, `GET /commerce/v1/offers/{id}?revision=N` returns a scoped immutable verified snapshot and link/evidence references. Unknown scope returns 404; expired facts return 410 or a typed non-publishable snapshot when historical-read capability is present. `GET /commerce/v1/content/{id}?revision=N` and `GET /commerce/v1/brand-kits/{id}?revision=N` return only pinned manifests. Artifact downloads are separate, scoped, hash-checked and size-limited; manifests cannot name arbitrary filesystem locations or URLs to fetch.

On MeuAssistente, `POST /commerce/v1/drafts` proposes one response grounded in supplied verified offer/content references and an opaque conversation handle. The service checks current ownership/consent and expiry, then uses a reviewed commerce adapter/tool/grounded-rendering extension. It returns a local draft reference with fact versions, not a sent message. The current restaurant renderer and business tools do not already support this schema; the first implementation uses fixtures/FakeClient and no external channel.

Future `POST /commerce/v1/communication-intents` admits one specific communication intention. Input binds immutable content/fact hashes, opaque recipient handle, exact channel/account, expected ownership/consent revisions, grant revision and validity window. Only a separately eligible production adapter and explicit `communication.send.v1` may dispatch. A caller cannot add contacts, infer consent, release human ownership, resolve an uncertain attempt or inject arbitrary factual prose through this endpoint. Without those later gates, return a typed refusal; do not route commerce through synthetic WhatsApp mode.

`GET /commerce/v1/operations/{operation_id}` on the owning execution endpoint returns the same durable typed receipt after restart. This is the first recovery action after timeout, credential expiry or disconnect. It never itself executes. A matching receipt can be replayed even when the original submission HTTP response was lost, subject to current read authorization. Expired/revoked authentication gives 401/403; refresh requires explicit preconfigured credential lifecycle, not a new operation or broader grant. If status remains unavailable, preserve uncertainty and stop dependent actions.

`GET /commerce/v1/conversations/{handle}/authority` on MeuAssistente returns only ownership state/revision, consent-purpose state/revision, suppression flag and authority expiry, with no message bodies or contact identifiers. This check is advisory until repeated inside the endpoint's dispatch fence. Future owner-only `POST /commerce/v1/conversations/{handle}/suppress` and `/handoff` require trusted operator authentication, expected revision and audit; they revoke/cancel pending AI work. A model/service send token cannot call them to release a human. Human release and consent creation/renewal remain explicit owner/recipient workflows, not a boolean in campaign input. Withdrawals must remain possible while publication/model quotas are exhausted.

`POST /commerce/v1/reports` on Zaturo admits a service-bound result report tied to an existing OperationId/task/campaign and monotonically increasing receipt/report revision. The principal cannot append arbitrary owner activity or forge another worker's job. Input carries period UTC bounds plus `America/Cuiaba`, content/receipt references, count provenance, currency-separated verified commissions, source-report cursors, known/pending costs, uncertainty and exception codes. The service checks evidence and projects an ordinary Hub feed item with one stable dedupe key. Full typed report is at most 8 KiB; owner summary at most 4,096 bytes, matching existing FeedItem. No raw recipient history, model reasoning or media enters the ordinary feed.

## Effect receipts versus Hub task states

The proposed `EffectReceipt` has OperationId, parent TaskId, account/channel, intent/content hashes, accepted grant revision, local authority revision, request/provider IDs, timestamps, receipt revision, evidence references and `effect_state`:

- `prepared`: locally persisted intention; no network send admitted yet.
- `accepted`: receiving endpoint durably admitted bounded work; no external effect asserted.
- `dispatching`: send boundary persisted before external IO; a crash here is potentially uncertain.
- `confirmed`: provider-specific authoritative evidence meets the exact adapter acceptance contract; retain what was confirmed (for example created post ID), without implying view/delivery/conversion.
- `rejected_no_effect`: authoritative refusal proves this attempt caused no effect.
- `uncertain`: effect may have occurred; quarantine, read-only reconciliation, no automatic resubmission.
- `cancelled_before_dispatch`: local evidence proves no external call was admitted.

These are proposed remote-effect states. Existing Hub `TaskState` remains CREATED, QUEUED, ASSIGNED, RUNNING, WAITING_APPROVAL, PAUSED, RETRY_PENDING, COMPLETED, FAILED, CANCELLED. Never serialize `uncertain` as a new TaskState without a separately reviewed change. A service-admission task may complete only its declared admission contract and keep a receipt saying accepted; later reconciliation/report tasks use the same existing Engine. A publication-success result requires a confirmed receipt. Unknown effects produce an exception/paused-or-failed task according to legal transitions; a generic hub retry must not regain send authority. A cancelled Hub task cannot undo an already admitted remote effect.

For WhatsApp experimental UI, an observed bubble remains UNCERTAIN under the existing contract. Do not manufacture `confirmed` from DOM visibility. Affiliate conversions and commissions require authorized program reports and their own evidence; publication confirmation is unrelated.

## Idempotency, recovery and limits

First valid mutation atomically persists scoped key, semantic fingerprint, receipt and audit before returning 202 Accepted. An exact duplicate returns the same receipt (200 replay or 202 still accepted), without new inference or external IO. Same key with different body/scope/hash returns 409 `idempotency_conflict`; stale expected revision returns 409 `stale_revision`. Concurrent first requests serialize on the unique scoped key. Reusing the same OperationId with a different key is also refused. Proposed tombstones retain scope/key/hash/final status for at least 180 days, configurable upward to the provider reconciliation/retention requirement; deleting personal payloads must not recreate execution authority. Legal retention review may shorten identifying data while keeping opaque dedup tombstones.

Use 400 for malformed schemas, 401 missing/expired credentials, 403 denied capability/purpose, 404 hidden/not-found scope, 410 expired content/grant, 413 oversized body, 422 invalid evidence/claim/link, 429 bounded admission and 503 unavailable dependencies. A 5xx or timeout after send is never proof of no effect. Reconciliation can confirm an authoritative provider receipt, establish no effect, or remain uncertain. A new attempt after proven-no-effect still requires current standing grant, time window, budget and bounded retry policy; an uncertain attempt never qualifies.

Initial proposed bounds: service body 32 KiB; canonical ID 128 bytes; SHA-256 64 hex bytes; at most 5 offers/3 drafts per batch; text 8 KiB before stricter channel limits; 30 future occurrences; 1 external effect in flight; page size 1..50 and opaque bounded cursors; 5-second service request deadline; at most 2 transport attempts only for read-only or proven pre-admission failures. Initial rate limit 60 reads/minute and 10 mutations/minute per principal, plus lower campaign/channel caps. Limit 8 service principals. No background unbounded polling: status uses bounded backoff with a persisted cursor and a circuit breaker. Media bytes use the existing artifact/transfer boundary with per-format size policy. Measure and revise bounds through explicit configuration review.

Acceptance requires version/auth/scope denial, stale fact/grant/consent rejection, conflicting replay refusal, restart-preserved receipt, lost-response recovery without another effect, withdrawal/takeover during dispatch, expiry during partition, no credential/PII in reports, and old Hub/worker compatibility. See [test plan](10-TEST-AND-ACCEPTANCE-PLAN.md). No mock proves real platform publication or eligibility.
