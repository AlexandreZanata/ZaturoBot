# Installed OpenCode execution

The registered integration ID is `installed-opencode`.

This is an additive typed execution path. Physical acceptance is separate from source tests
and installation. It requires a compatible hub, the work worker and the owner's native
clients. Do not substitute the previous direct Python generation path as OpenCode evidence.

## Intent and authority

Known explicit generation commands normalize without a routing model call. The exact alias
`falllem price` maps to `fallem-prince`; existing aliases and count1..10 remain. The resulting
`youtube_opencode_generate` task requires `youtube.opencode.v1`. Its installed OpenCode
session makes one DeepSeek tool-selection call before the broker invokes generation.
Unknown conversation creates `assistant_route` with bounded ordinary context (four turns,
1024 bytes). A target advertising `assistant.route.v1` interprets locally; otherwise the
configured assistant worker is selected. An older default worker that advertises only
`assistant.chat.v1` retains text-only ordinary chat; it is never claimed as an action
router or installed executor. Only relevant registered schemas are disclosed.
The model returns reply, clarify or a typed registered action. Hub services independently
validate it against the original request and current worker capabilities, then atomically
create at most one child under `route-PARENT_OPERATION`. The trusted planner identity is
bound by the hub, not supplied by the model. Browser planning remains on its existing
home worker. A route proposal never grants capture, input, upload, scheduling or shell.

Negation, hypothetical wording, malformed counts, extra operations and unknown channels
cannot be promoted to generation by a model. Additional operations require a separate
owner request. A generation-only task never invokes YoutubeBot's general run or submit.

## Actual installed program

The runner verifies a trusted absolute executable, SHA256 and exact OpenCode2.3.0 version.
The reviewed upstream tag is v2.3.0, commit
a6b15d33daf6ab7d35569f6d711fdb630b9f04e7. The supported standalone run interface uses
explicit model, agent, session, title and JSON output; `--auto` is forbidden. Work orders
bind operation/task UUIDs, target, purpose, count/channel or bounded routing context,
deadline and exactly one model/tool call. Runtime is at most150s, output65536 bytes,
and the deadline at most180s. Private intent is created exclusively and fsynced before
launch. Existing intent means reconciliation, never a new model session.

A private project profile configures the V2 default-deny permission/policy arrays, one
job MCP server, no shell/read/edit/execute/subagent tools, no web search, snapshots,
sharing, warming, compaction or external plugins, and the exact flash model. The installed
binary's metadata-only `debug config` must parse this profile before paid acceptance.
Job files are mode0600 under0700 directories. They contain approved text and metadata,
never raw reasoning, provider keys, worker/admin credentials or pixels.

The runner owns `zaturo-opencode-UUID.service`, with CPU100%, MemoryHigh512MiB,
MemoryMax2GiB, TasksMax128, runtime bound, no restart and group cleanup. It records actual
MainPID, executable, process-start ticks, cgroup, session and hash. A clean `env -i`
environment keeps only owner/local-session routing. The existing protected OpenCode Go
integration supplies authentication. No home provider key is copied or provisioned.

## One-attempt Go gate and tool broker

Upstream2.3.0 has internal retry logic; agent steps alone cannot enforce one paid attempt.
A random-header loopback gateway therefore permits one forward in total. It uses the
existing worker's durable aggregate Personal ledger for reserve, settle and uncertainty,
explicit Personal/Go configuration, the fixed Go endpoint, and only
`deepseek-v4.1-flash`. Automatic OpenCode history/file context is discarded at the gateway;
only the reviewed bounded work order, relevant schemas and ordinary route context go out.
There is no Console/model/credit fallback or automatic purchase. Keep Extra Usage off.
Owner-reported balance is not independently observed billing configuration. Actual replies
must prove Go/go-plus and reported cost zero before any tool response is released.
Missing usage/billing is uncertainty, not free usage. Private reasoning is removed.

The only model-visible MCP tool is `youtube_generate` for a generation order or
`select_action` for interpretation. Its exact schema is job-scoped. The broker independently
checks arguments, active deadline, actual process and settled subscription receipt, and
allows only one invocation. The generation adapter executes fixed argv:

```text
CONFIGURED_PYTHON -m tools.ytbot.service generate --operation-id SAME_UUID --channel CANONICAL --count COUNT --approved-generation
```

No task supplies an executable, root, account, shell, filesystem path or ADB string.
The broker never calls `bot_chat`. It persists media dispatch proof before invoking Python.
A random result receipt observed in an actual OpenCode `tool_use` event proves that the
installed session received its broker result. The dispatch session then stops; deterministic
host status observation owns the long media lifetime without model polling.

## Recovery, cancellation and media

The same UUID binds hub task, worker journal, OpenCode session/work order/broker and Python
job. After a lost response, only status/reconciliation of that UUID is allowed. No intent,
execution fence, active reservation or media file is deleted to make a retry possible.
Generation remains distinct from the owner's preexisting scheduled operation.

`cancel_owned` requires this executor's private durable generation intent/proof, exact
request/mode/count/channel, current UID, Python executable, project cwd, fixed actor argv,
PID/start ticks, cgroup and unit MainPID. Only that unit can be stopped. Post-stop inactive
state and vanished actor must both be proved. It preserves all Python fences/media and
records cancellation metadata; the Python outcome remains uncertain until reconciled.
Runtime task cancellation uses this contract if the broker may have admitted media.
Stopping only OpenCode or cancelling a hub admission task is never proof of media stop.
After admission has become a terminal hub task, a generic hub cancel cannot cancel the
background actor; use this operation-bound host API, not global process signals.

Before announcing OpenCode generation complete, the host requires matched completed
mode=generate status, count ready distinct runs, generated_count=count, scheduled_count0,
failed_count0 and actual video files. Fixed ffprobe/ffmpeg inspect duration and audio/video
streams, compute SHA256 and fully decode with `-xerror`; output, time and process groups
are bounded. Each video must have a render mtime at or after this operation's admission; an older
ready video cannot be counted as newly produced. Acceptance also records the pre-submit
run/stage inventory to distinguish newly rendered runs from explicitly resumed stages.
Files are checked for stable identity/size/mtime and duplicate byte hashes
are rejected. Inspection receives paths only from ready run IDs under the configured
runs root. Curated `VideoArtifactEvidence` has opaque refs and media/tool hashes, no paths.
Private cached decoding evidence is reusable only after rehashing the same ready files.
Failed media proof produces uncertain history, never a fabricated success or another batch.

Ordinary media access uses existing explicit age-encrypted device transfers and their
actual per-file/spool/pending/TTL quotas. Opaque artifact refs alone are not a delivered
transfer. Record the real approved transfer IDs after upload/delivery verification.
No private account/profile/media or sensitive evidence belongs in GitHub.

## Rollout and acceptance

Install the compatible hub before advertising the new capabilities. Preserve schema9 hub
and schema8 worker journals, all keys, current units and the original YoutubeBot checkout.
The work installer accepts a nonsecret `--opencode-config` and explicit
`--enable-generation --enable-opencode`; it never enables these merely from a path.
Provider configuration has no key field and reuses the existing protected integration.

Run focused synthetic tests, `cargo xtask check` and `cargo xtask secrets` before publishing.
Native Android changes must be built with the existing signing identity, preserving data
and enrollment. Real acceptance needs the exact owner chat, actual billed Go/installed
program/tool receipts, a separate generation-only batch of two real videos, full media
proof, no new publication records, Hub transitions, approved encrypted transfers, actual
backend browser observations, native-consented PC capture and enrolled USB navigation/
phone-view delivery. A native displayed receipt is separate from frame upload readiness;
it records only fixed metadata after the visible foreground decode/render path.
A successful config probe, doctor, launch or admission proves only
that specific step. Report VERIFIED/BLOCKED/NOT IMPLEMENTED without conflating them.

Registered browser research retains its durable routing origin. Hub validates that origin
on both child creation and executor grant, and permits only public browser reads; neither
model output nor native approval expands it into desktop observation, input or social
actions. Explicit general computer tasks retain their separate bounded native grants.


A missing CLI result acknowledgment cannot orphan positively admitted media: the host
observes the same operation once, marks `opencode_result_observed=false` honestly and
continues deterministic monitoring only if the media service positively confirms admission.
Even a completed media status recovered during dispatch remains an admission result until
the separate full artifact inspection confirms completion. No model or batch is replayed.
